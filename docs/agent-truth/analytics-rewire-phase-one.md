# Analytics Rewire Phase One

Status: static inventory and authority-map contract

## Purpose

This rewire inventory exists so future analytics work starts from a deterministic map instead of another broad audit. It records the current telemetry, parity, snapshot, Debug, score, and release-version lanes before runtime refactors begin.

The report is generated by:

```bash
npm run check:analytics-rewire-phase-one
```

The generated snapshot is:

```text
agent/state/analytics-rewire-phase-one.generated.json
```

## What It Proves

The validator proves only local/source facts:

- the inventory contract exists
- required truth lanes have owner recommendations
- duplicate snapshot authority is recorded
- raw admin display fallback risks are recorded
- vendor evidence boundaries are recorded
- stale generated-report risk is recorded
- orphan/lost-data candidates have recovery fields

It does not prove production data exists, current production counts, provider health, BigQuery freshness, GA4 parity, PostHog parity, Firebase billing state, or screenshot readiness.

## Canonical Owner Recommendations

- Raw event ledger: first-party product behavior facts such as `analytics_event_facts`, `analytics_guest_batches`, watch sessions, purchase facts, unlock facts, notification facts, and route diagnostics.
- Identity graph: anonymous visitor, session, user, creator, admin, and system linkage without rewriting old guest facts.
- Admin metric snapshot: compact Admin Analytics display truth.
- Admin Debug parity: formulas, source breakdowns, drift, missing samples, stale state, and recovery detail.
- Vendor evidence: GA4, PostHog, and BigQuery validation/export lanes.
- Release/version truth: Beta badge release notes and public changelog artifacts.
- Readiness score/evidence: generated public beta, launch readiness, PR triage, and score reports.
- Cloud/Firebase cost truth: static cost guardrails, route contracts, and provider cost evidence when explicitly requested.

## Snapshot Authority Rule

`analytics_admin_metric_snapshots` is the recommended canonical Admin Analytics module/display snapshot layer.

`analytics_aggregate_stats/realtime_summary` remains a legacy, fallback, live-pulse, or evidence source unless a specific existing route explicitly owns it. Future rewire phases should collapse display authority toward `analytics_admin_metric_snapshots` and keep raw collections or realtime summary details in Debug.

## Raw Ledger, Snapshot, Debug, And Vendor Roles

Raw ledger data is product behavior source, but raw rows are not automatically unique users, sessions, funnels, bounces, live presence, or launch readiness.

Verified snapshots are Admin Analytics display truth because they carry source labels, freshness, validation, and fake-zero protection.

Admin Debug is the place for raw collection names, formulas, source counts, confidence, drift, stale state, and recovery findings.

GA4, PostHog, and BigQuery are evidence or export lanes unless reconciled and visibly labeled. They must not override first-party snapshot truth.

## Lost Data Definition

Lost data means data that may still exist but is not visible where operators expect it. Examples:

- written but not materialized
- materialized but not consumed
- consumed but filtered out
- visible in Debug but not Admin Analytics
- stuck under guest, anonymous, session, or legacy identity keys
- excluded by actor classification
- hidden behind stale snapshots
- stored under legacy field names
- exported to GA4, PostHog, or BigQuery without first-party reconciliation

The Phase One report lists candidates only. It must not be used as a deletion plan.

## Cost Boundaries

The validator is static and local. It must not:

- read production Firebase
- query BigQuery
- call GA4, PostHog, PayPal, Cloud Run, or Firebase production APIs
- add listeners
- add scheduled jobs
- run Playwright, Cypress, Lighthouse, or full `npm run check`
- treat `LIMIT` as a BigQuery cost-control strategy

Future runtime changes should reduce repeated admin raw scans, prefer bounded snapshots, and label generated/cached evidence as fresh or stale.

## Future Use

Future phases should use the report to:

- pick one owner for each duplicate metric
- recover high-value guest, journey, watch, support, notification, purchase, and unlock data
- decide which raw lanes stay Debug-only
- decide which legacy lanes become deprecated candidates
- add validator locks before runtime consolidation
- keep release/version evidence current after accepted patches

The report must not:

- claim production analytics health
- claim provider smoke passed
- claim screenshot QA passed

- mark stale data as live

- rewrite event emitters
- change Admin Analytics runtime behavior
- override higher-authority doctrine or verified runtime code
