# KandyDrops Product Constitution

Authority level: 1

This constitution is the highest human doctrine for product, business, user-loop, and brand constraints. It supersedes older product doctrine fragments when they conflict.

## Product Loop

- KandyDrops sells digital Drop unlocks and creator experiences through a GumDrop economy.
- The core loop is discover -> understand value -> refill or spend -> unlock -> view -> return -> deepen creator affinity.
- Paid, reward, entitlement, and creator-monetization states must be understandable before a user spends.
- Locked content must sell the idea of the Drop without exposing protected internals.

## Brand And Copy

- KandyDrops uses direct, human, high-trust copy. Avoid generic SaaS filler and fake urgency.
- Product copy may be playful, but payment, security, support, unlock, and account states must be precise.
- Use approved vocabulary: GumDrops, Drops, unlocks, creators, fan experiences, and support tickets.
- Do not reintroduce legacy economy words like Coins for user-facing GumDrop value.

## User Trust

- Never show a fake green/healthy/pass state when source truth is missing, stale, fallback, partial, failed, or unknown.
- Payment and unlock flows must be reversible in support terms: a human should know what happened, where, and why.
- Screenshots are UI evidence only. They are not proof of security, moderation, payment, unlock, or analytics truth.

## Business Constraints

- Revenue is anchored to server purchase or ledger truth, not client-only events.
- Unlock count is anchored to server entitlement truth, not UI success state.
- Creator monetization must respect paid-source GumDrop eligibility.
- Admin QA, owner behavior, and projection events must not inflate user behavior, creator activity, or revenue.

## Winning Rule

If product doctrine conflicts with lower-authority docs, this file wins for product intent. Runtime code and verified configuration still prove what the app currently does.
